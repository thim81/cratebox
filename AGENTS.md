# Repository instructions

- The user does not like Git worktrees. Work in the current checkout by default; create a worktree only when the user explicitly asks for one.
- For local UI work and interactive verification, use the Codex embedded browser; do not switch to an external browser or native Chrome. Verify behavior in the embedded browser when the app and required local services are available, rather than relying only on a build.
- Custom MCP source, tests, Python project configuration, lockfile, and setup documentation live in `cratebox/rekordbx-mcp/`. Run uv from that directory, or use `uv --directory cratebox/rekordbx-mcp ...` from the repository root.

## Application domains

- **CrateBox UI** presents playlists and collection results and handles user interaction. It talks to the CrateBox API, not directly to Rekordbox or the Rekordbox MCP.
- **CrateBox API** is the UI's application interface. It coordinates playlist operations and collection lookups, and serves audio to the UI. It owns app-specific behavior and keeps local file paths on the server; browser responses must not contain audio paths. CrateBox may update embedded cover artwork or the embedded star rating of an MP3/M4A selected from an app-owned crate or resolved by its track ID in the Rekordbox collection. Rekordbox audio-tag edits do not require playlist membership. Rating edits must target the track loaded in the deck. Change only the selected artwork or rating tag and preserve existing ID3v1 bytes verbatim. Stage and verify the update before atomically replacing the selected audio file; preserve audio data and all other metadata values, and do not retain a backup. These audio-tag permissions do not authorize other audio edits. Rekordbox playlist writes are governed separately below.
- **Rekordbox MCP** provides generic collection reads and permitted playlist mutations. Read the original Rekordbox database directly and use the same serialized integration for permitted playlist writes. Reuse the pinned upstream MCP and pyrekordbox operations where they fit; add only the missing generic operations. Do not add CrateBox-specific tools, configuration, playback behavior, or assumptions to the MCP. Consumers such as the CrateBox API adapt the generic MCP contract to their own features.

- **Controlled Rekordbox playlist editing is permitted.** Support two playlist modes: local CrateBox playlists, editable independently of Rekordbox, and Rekordbox playlists linked to an existing playlist in the original database. Permitted database changes are limited to creating playlists and editing playlist names, membership, and order; preserve existing playlist IDs when editing. Required library-managed playlist companion-file updates (including masterPlaylists6.xml) are permitted and must be covered by backup and recovery. This does not authorize deleting playlists or changing track metadata, cues, beatgrids, XML exports, analysis files, or unrelated collection data.
- **Playlist edits save immediately after the user's editing action.** Dropping tracks into a new order, choosing a replacement song, adding or removing songs, and creating or renaming a playlist authorize the corresponding database operation. Do not require a separate Save button, confirmation dialog, or pending-draft workflow. If Rekordbox or its agents are running, reject the edit with a clear message to close them; do not silently queue or retry it. Report success only after the write succeeds, and preserve or restore the UI's previous state on failure.
- Implement and verify database backup and recovery before enabling writes to the original Rekordbox database. Create and verify a recoverable backup before the first edit in a writer session, then before an edit when the last verified backup is at least five minutes old, following upstream's 300-second backup cooldown policy. Store backups outside the original database directory, use a consistent encrypted-database backup or controlled copy, and include required playlist companion files; upstream's warning-only copy failure handling must not permit writes. Reuse that verified backup during the cooldown rather than copying the database for every edit; do not run backups while idle. Check that Rekordbox and its agents are closed at startup, before opening a database connection, and immediately before committing a playlist edit. Reject access if the check fails. Backup and restore check the processes at their own database access boundaries. Detect conflicting playlist changes before editing. Use short database transactions and handle lock failures without automatic mutation retries; process checks do not guarantee perfect mutual exclusion. Serialize writes, including backup decisions, and validate the result; perform compound edits such as a song swap in one transaction. A failed required backup must block the write. Fail without writing when prerequisites cannot be verified. Developing this feature does not itself authorize live database writes during development or testing.
- Keep it simple and safe. Reuse existing tested operations. Give each safety check one clear owner and a specific failure it prevents. Keep implementation details in code and tests.
- Use playlist-entry IDs for moves, removals, and swaps. Preserve unaffected entries and their relative order. Use temporary byte-for-byte copies or synthetic databases for inspection and testing. Audio files remain read-only except for the explicit CrateBox embedded-cover and loaded-track rating operations described above. Write exports and test artifacts outside the original Rekordbox data locations.
- Use uv for Python environments, commands, and tests. Use the native macOS launcher; do not use Docker.
- CrateBox API source and tests live in `cratebox/`; MCP source and tests live in `cratebox/rekordbx-mcp/`.
- Configure MCP clients to launch `rekordbx-mcp start` against an explicit original database path. Open the configured database for each request and close it afterward. If Rekordbox or its agents are running, report that they must be closed and let the user retry. Keep a tool allowlist limited to permitted operations. The worker uses normal user permissions; do not claim OS filesystem or network isolation.
- Keep upstream unmodified and pinned. Use `rekordbx-mcp update-upstream` for explicit upgrades with compatibility tests and rollback. Upgrading must not automatically expose new tools or weaken direct-access process checks or controlled playlist-write safeguards.
- Playlist export accepts either ordered track IDs or ordered absolute file locations, resolving both through the connected collection. File locations must match exactly one active collection track; never export unregistered files. The playlist exporter may insert only the fixed separator WAV references from the user's supplied separator folder, and each must resolve to exactly one active collection track. Write M3U8 files only in the repository's `playlists/` directory and CrateBox JSON metadata in `.cratebox/crates/`. Existing JSON files in `output/` stay untouched and are not read or migrated. Update existing files only after explicit user confirmation, follow no destination-directory symlink, and keep file export separate from controlled Rekordbox playlist saves; the exporter itself must not import into Rekordbox. Keep audio paths out of browser API payloads and conversational MCP client allowlists. Any path access needed by a local application must use a generic MCP data contract; keep app-specific decisions and playback in that application's API. A separate playlist uses a different name. The exporter creates external files, so its MCP annotation must not claim it is read-only.
