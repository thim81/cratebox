# Repository instructions

- The user does not like Git worktrees. Work in the current checkout by default; create a worktree only when the user explicitly asks for one.
- For local UI work and interactive verification, use the Codex embedded browser; do not switch to an external browser or native Chrome. Verify behavior in the embedded browser when the app and required local services are available, rather than relying only on a build.
- Custom MCP source, tests, Python project configuration, lockfile, and setup documentation live in `rekordbx-mcp/`. Run uv from that directory, or use `uv --directory rekordbx-mcp ...` from the repository root.

## Application domains

- **CrateDeck UI** presents playlists and collection results and handles user interaction. It talks to the CrateDeck API, not directly to Rekordbox or the Rekordbox MCP.
- **CrateDeck API** is the UI's application interface. It coordinates playlist operations and collection lookups, and serves audio to the UI. It owns app-specific behavior and keeps local file paths on the server; browser responses must not contain audio paths. CrateDeck may update cover art in place only for an MP3 resolved from a selected entry in the repository's own `playlists/` folder, after writing and verifying an exact backup under `output/audio-backups/`; this does not authorize any other audio or Rekordbox data edits.
- **Rekordbox MCP** is a consumer-neutral data provider for the local Rekordbox collection. It owns snapshot-backed collection access and exposes generic collection data and operations. Do not add CrateDeck-specific tools, configuration, playback behavior, or assumptions to the MCP. Consumers such as the CrateDeck API adapt the generic MCP contract to their own features.

- **Never change or alter the original Rekordbox database, playlists, XML exports, analysis files, or metadata.** Audio files remain read-only except for the explicit CrateDeck artwork operation described above. Use temporary byte-for-byte copies or exported snapshots for inspection and testing, and write generated artifacts only outside the original Rekordbox data locations.
- Use uv for Python environments, commands, and tests. Use the native macOS launcher; do not use Docker.
- CrateDeck API source and tests live in `neon-crate/`; MCP source and tests live in `rekordbx-mcp/`.
- Configure MCP clients to launch `rekordbx-mcp start`: require Rekordbox and its agents to be closed, create and verify a fresh read-only snapshot, then launch the MCP against that copy. Startup must fail if checking or copying fails; never silently reuse an old snapshot. Keep the explicit snapshot path, read-only connection, SQL authorizer and tool allowlist. The worker uses normal user permissions; do not claim OS filesystem or network isolation.
- Keep upstream unmodified and pinned. Use `rekordbx-mcp update-upstream` for explicit upgrades with compatibility tests and rollback. Upgrading must not automatically expose new tools or weaken the snapshot or read-only database protections.
- Playlist export accepts either ordered track IDs or ordered absolute file locations, resolving both through the verified snapshot. File locations must match exactly one active snapshot track; never export unregistered files. The playlist exporter may insert only the fixed separator WAV references from the user's supplied separator folder, and each must resolve to exactly one active snapshot track. Write M3U8 files only in the repository's `playlists/` directory and matching JSON plans only in `output/`; update existing files only after explicit user confirmation, follow no destination-directory symlink, and import nothing into Rekordbox. Keep audio paths out of browser API payloads and conversational MCP client allowlists. Any path access needed by a local application must use a generic MCP data contract; keep app-specific decisions and playback in that application's API. A separate playlist uses a different name. The exporter creates external files, so its MCP annotation must not claim it is read-only.
